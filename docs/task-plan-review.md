# タスク計画レビュー

> この資料は設計と配布フローへの実装確認事項を示す。配布フローへの適用は各実装箇所で別途検証する。

## 目的と責務

artifact-workflow の親は、ユーザーとの対話、既存ソースの調査、仕様の具体化、実行可能で競合しにくい具体的タスクへの分解を担う。仕様上の不明点は原則一つずつ質問し、回答に応じて確定仕様を更新する。通常の質問ごとに subagent を起動しない。

親は[Reviewer Asset](../plugins/artifact-workflow/skills/artifact-review/assets/reviewer.md)に従って独立 Reviewer へ委任する。Reviewer は読み取り専用で確認し、編集、外部更新、再委任をしない。仕様対話、指摘の採否、計画修正、承認判断は親が担う。

分解を終えた計画案は、ユーザーへの提示・承認前に原則1回、既存の `artifact-review` Skill と同じ独立 Reviewer subagent で確認する。仕様理解・タスク分解専用 agent や独立 Skill は追加しない。計画レビューは固定の工程別観点を用い、計画内の成果物タスクへ適用する共通方針とは別に扱う。共通の5原則は[レビュー原則](../plugins/artifact-workflow/skills/artifact-review/references/review-principles.md)を再利用する。

流れは親による仕様具体化、タスク分解、Reviewer による計画レビュー、親からの最終タスク一覧提示とユーザー承認、生成、成果物レビューとする。計画レビューは承認や計画保存を代行しない。

## 計画レビューの入力と観点

親は Reviewer に次の情報を渡す。会話の要約だけに依存せず、元要求と確定仕様の根拠を独立に確認できるようにする。

- レビュー種別が計画レビューであること、親識別子、計画全体を対象とする依頼を識別する情報。
- 元のユーザー要求とユーザーが確定した回答の本文または参照先。
- 確定仕様と、残っている不明点。未決事項が計画の判断を妨げる場合はその影響。
- 計画の範囲、計画案全文、識別可能な対象版。
- 関連ソース・構造と対象版、独立確認に必要な参照先。
- 再レビューでは、前回の指摘、親の採否と理由、修正内容と影響範囲、新しい計画案版。

承認前レビューは計画全体を対象とする。タスク単位レビューID、承認根拠、生成成果物を要求しない。

Reviewer は元要求・確定回答を読み、関連ソースを独立に確認して、次の固定観点をそれぞれ評価する。

1. **仕様の具体性**: 要求と確定回答から、目的、制約、未決事項を十分具体的に把握できるか。
2. **要求の充足性**: 計画全体が合意済みの要求を過不足なく実行可能な作業へ反映しているか。
3. **タスク自体の妥当性**: 各タスクの責務、粒度、実現可能性、成果物、実物で判定できる完了条件が適切か。
4. **タスク間の整合性**: 依存、順序、共有領域の競合が明確で、実行可能な分割になっているか。

共通5原則もすべて再利用するが、上記4観点とは別の共通基準であり、4観点へ数えない。

## 返却と記録

返却では、親識別子と依頼識別情報、レビュー種別、対象計画案版、状態、根拠のある確認範囲・方法を対応づける。状態は既存 Reviewer 契約の `reviewed`、`input_insufficient`、`inconclusive` を用いる。計画全体への指摘は計画内の箇所、個別タスクへの指摘はタスクIDを示し、指摘ID、分類（要修正または任意提案）、関係する要求・観点、問題と影響、根拠、必要な対応を含める。未確認事項と阻害要因も、対象・影響・再開に必要な情報と結びつける。入力不足、結論不能、未実施を問題なしと扱わない。厳密な新規 JSON schema は設けず、既存の [Reviewer Asset](../plugins/artifact-workflow/skills/artifact-review/assets/reviewer.md) の契約を拡張して扱う。

元要求・確定回答の根拠、計画案版、レビュー対象版と結果、親の採否理由は既存の会話・引継ぎ記録で保持する。計画案版を MCP の `revision` と混同せず、計画案を新しい版へ直したら版識別を更新する。旧版へのレビュー結果を新版へ転用しない。

## 計画ライフサイクル

計画レビュー用の draft は親の会話・引継ぎ記録で版管理し、MCP に `save_plan` しない。既存の[計画ライフサイクル](../plugins/artifact-workflow/skills/artifact-workflow/references/task-memory.md)に従い、新規フローの開始前に親が一度だけ `initialize_session` を行い、同一フローの親・Reviewer・worker は同じ `sessionId` を共有する。計画レビュー時の `get_plan` で `plan: null` が返ってもレビュー失敗とはしない。

レビュー成立後の最終タスク一覧の提示と、承認または明示的省略根拠の確認は「指摘対応と終了条件」に従う。親は既存の[承認方針](../plugins/artifact-workflow/skills/artifact-workflow/references/approval.md)に従い、必要な承認条件を満たした後に合意済み計画を `save_plan` する。保存成功を確認してから生成を開始する。

## 指摘対応と終了条件

**要修正**は、要求・確定仕様・制約との不一致、判断を妨げる入力不足や未確認、実現不能なタスク、完了条件の欠落、依存・競合の問題など、計画の実行可能性や要求達成に影響する指摘とする。**任意提案**は、要求達成と安全な実行を妨げず、任意の明確化・改善に留まる指摘とする。親は採否と根拠を記録し、要修正を根拠なく任意提案へ格下げしない。

親は要修正と、計画成立に必要な未確認事項を解消する。仕様判断が必要ならユーザーへ追加質問し、回答を計画に反映する。要求、責務、依存、完了条件を実質変更した場合、重大指摘の是正を独立確認すべき場合、または変更の影響が不明な場合は再レビューする。意味を変えない表記修正など、親が差分確認で影響なしと判断できる軽微な修正は再レビューを省略できる。その場合、親は旧版のレビュー対象、修正版、判断理由、確認根拠を記録し、修正版自体は独立レビュー済みと表現しない。古い結果を変更の影響箇所へ根拠なく流用しない。任意提案だけを理由に反復しない。

重大な未解決指摘がなく、必須修正と必要な未確認事項が解消されたら、親はレビュー結果と修正後の状態を区別して記録し、最終タスク一覧をユーザーに提示して既存の承認フローへ進む。再レビューが必要な変更はその新版についてレビュー成立を確認する。入力不足、結論不能、未実施、対象版不一致、重大な未解決指摘がある状態では問題なしやレビュー成立と判定しない。修正判断、ユーザー回答、再レビュー要否とその根拠は既存の会話・引継ぎ記録に残す。

## モデル選定と記録

親は Reviewer の独立検証の品質と高い思考力を重視し、計画の性質・役割・実行環境で利用可能なモデルを確認して、根拠に基づきモデルと必要な推論強度を選ぶ。固定モデル名や順位は設けない。`collaboration.spawn_agent` が `model` と `reasoning_effort` を受け付ける環境ではそれらを指定できる。上書き時に `fork_turns: "none"` を要求する API では、必要な依頼・文脈・資料を新しい context へ明示的に渡す。毎回、利用可能な API の実 schema と制約を確認し、他環境へ前提を一般化しない。指定値と実効値は区別し、起動結果が実効値を示さなければ未確認とする。候補・指定の確認ができない場合は既定・継承へフォールバックし、理由と選定根拠を既存記録に残す。[Subagents のモデル設定](https://learn.chatgpt.com/docs/agent-configuration/subagents)を指定・継承の参考にし、詳細な運用は[モデル選定・起動・記録](../plugins/artifact-workflow/skills/artifact-workflow/references/model-selection.md)を正本とする。

## 検証観点

実装時は[製造・レビュー観点](manufacturing-review.md)と[テスト・検証観点](testing-review.md)に従い、少なくとも次を確認する。

- 仕様具体化からタスク分解、独立計画レビュー、ユーザー提示・承認、生成・成果物レビューまでの順序と親・Reviewer の責務境界。
- 元要求・確定回答・残る不明点、計画全文と対象版、関連ソースと対象版、再レビュー情報を Reviewer が受け取れること。
- 固定4観点と共通5原則を別枠で適用し、登録型レビュー拡張の上限に混ぜないこと。
- 計画全体レビューが承認根拠、生成成果物、タスク単位レビューID、`get_plan` の非null計画に依存しないこと。
- 指摘分類・対象箇所、未確認・阻害、必須修正、任意提案、影響に応じた再レビューと終了条件が区別されること。
- `initialize_session` の回数と `sessionId` 共有、draft の非保存、`plan: null` の扱い、承認後の `save_plan` 成功確認が既存契約に整合すること。
- 実質変更・重大指摘の是正・影響不明時に新版を再レビューし、軽微な変更を親が差分確認で済ませた場合はその判断根拠が残り、修正版を独立レビュー済みと誤記しないこと。旧版結果を変更の影響箇所へ流用せず、入力不足、結論不能、未実施、重大な未解決指摘を成功扱いしないこと。
- モデル指定とフォールバックが実際の API schema に従い、実効値未返却を未確認として扱うこと。
