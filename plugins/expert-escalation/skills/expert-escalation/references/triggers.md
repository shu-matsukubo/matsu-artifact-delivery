# 呼び出すタイミング

「難しい」「不安」「変更ファイル数が多い」だけでは呼ばない。次のいずれかについて、**具体的な観測事実、影響する必須条件、相談によって決めたいこと**をそろえたときに自動相談する。点数の合計やファイル数だけで機械的に発火させない。

| ID | エスカレーション条件 | 入力に残す証拠の例 |
| --- | --- | --- |
| D1 設計の行き詰まり | 異なる設計案を少なくとも2案比較し、各案が必須条件のどれかを満たせない。または必須条件同士の矛盾を具体的に示せ、承認済みの範囲で成立する設計を選べない。 | 案A/B、満たせない条件、確認した仕様や小規模な検証結果。 |
| S1 セキュリティ判断 | 保護対象、信頼境界、漏えい・権限逸脱・改ざんにつながる具体的な経路を示せるが、既存の対策で遮断できるか判断できない。または対策案が承認済みの必須条件と衝突する。 | 認可の境界、データの流れ、問題の箇所、対策が不十分と考える根拠。攻撃の実行は不要。 |
| I1 影響範囲の不確定 | 依存関係や利用箇所を調べた結果、共有契約・永続データ・複数の担当領域へ変更が波及し、影響する利用者、互換性の維持、移行・復旧方法、検証範囲のいずれかを確定できない。 | 影響先の一覧、未確認の利用箇所、破壊し得る契約、未確定の移行・検証事項。 |
| U1 根拠の不一致 | 一次資料・実測・既存実装の間に結論を左右する矛盾があり、対象バージョンや条件を合わせて調べても判断できない。 | 相反する根拠の参照先、確認した条件、結論によって変わる作業。 |
| F1 修正の停滞 | 同じ必須条件の失敗について、異なる原因仮説に基づく修正を2通り検証しても失敗が残り、次の修正を選ぶ根拠がない。 | 原因仮説、各修正、期待結果と実測結果、未解決の条件。 |

S1・I1では、相談の条件を満たすために危険な操作や不可逆な変更を試さない。D1・F1の比較や検証も、既存の権限と作業範囲内で行う。

## 相談を増やさない場面

- 誤字修正、既知の手順、理由の明らかな単純な失敗、根拠のそろった通常の実装・レビューは元の担当で進める。
- API名や手順の未確認だけなら、まず資料を読む。確認できる情報を調べずに「不明」として相談しない。
- 資料の場所、必要な入力、認証情報、実行権限がないだけなら、相談役でも解決できる論点かを切り分ける。事実の補完や権限の許可をモデルに代替させない。
- 予算・スコープ・リスク受容など人間だけが決める事項が確定している場合は、技術的な相談を繰り返さず、必要な材料を報告してユーザー判断へ戻す。

複数条件に該当しても、同じ問いなら1件にまとめる。異なる問いをまとめて作業全体を丸投げしない。利用条件に当てはまることは、上限を超える根拠にはならない。
