# 相談する論点の例

以下は、明示依頼の問いと入力を整理するための例であり、自動起動の条件ではない。相談を行うか、事前にどこまで比較・検証するかは、ユーザーの依頼と呼び出し元の方針に従って親が決める。

| 論点 | 相談したいこと | 入力に残す証拠の例 |
| --- | --- | --- |
| 設計案の比較 | 必須条件を満たす案を選ぶ、または条件同士の矛盾を解く。 | 候補案、満たせない条件、確認した仕様や検証結果。 |
| セキュリティ判断 | 具体的な漏えい・権限逸脱・改ざんの経路に対策が有効かを検討する。 | 保護対象、信頼境界、データの流れ、対策が不十分と考える根拠。 |
| 変更の影響 | 共有契約・永続データ・複数担当へ波及する変更の範囲と検証方法を整理する。 | 依存先、互換性、移行・復旧案、未確認の利用箇所。 |
| 根拠の不一致 | 一次資料・実測・既存実装の矛盾を、対象バージョンと条件に照らして検討する。 | 相反する参照先、確認条件、判断で変わる作業。 |
| 修正後に残る問題 | 試した修正が失敗した理由と、次に確かめる仮説を検討する。 | 原因仮説、修正内容、期待結果と実測、過去の助言と残る問い。 |

相談の材料を作るために、危険な操作や不可逆な変更を試さない。事前調査や検証も既存の権限と作業範囲内で行う。

資料・入力・認証・権限が足りないだけの場合は、相談役が判断できる問いかを親が切り分ける。予算・スコープ・リスク受容など人間だけが決める事項を、モデルの助言で代替しない。

複数の問題でも同じ問いなら1件にまとめる。再相談では前回の助言・検証結果と今回の問いを渡し、作業全体を実装担当として丸投げしない。
