# 計画の承認

- この Workflow では、通常の作成依頼を依頼内容の検討と計画案の作成・提示として扱い、それ自体を計画への承認とは扱わない。計画提示後の明示的な承認を得てから、計画を保存する。承認前に worker を起動したり、成果物を生成したりしない。
- 同じ計画への承認を得ている場合は再度求めない。依頼文で指定された成果物を作る許可と、計画そのものへの明示的な承認を区別する。通常の作成依頼や無応答は承認・省略指示とみなさない。
- 承認手続きの省略は、今回の作業に適用される利用者の明示的な指示がある場合だけ認め、根拠と適用範囲を記録する。
- 作業範囲・目的・成果物・完了条件を変更する場合は計画を更新して再提示し、承認を得る。
- `initialize_session` と `get_plan` は計画案を作るために利用できる。承認待ちを保存する値はなく、承認までは `save_plan`、委任、成果物の生成に進まない。
- 承認根拠のない委任は開始しない。
- 承認の判断と計画への記録は親が行い、`approval.evidence` は `approval.mode` に応じた根拠にする。`approved` の場合は計画全体と対応するユーザーの発言を記録し、提示後の明示的な承認発言を短く引用して対象計画を特定する。`waived` の場合は今回の作業に適用される明示的な省略指示と適用範囲を記録する。通常の作成依頼をどちらの根拠にも使わない。MCP は会話を参照せず、発言の出所や計画との対応を検証しない。
- 例：ユーザーが「この Workflow を使ってファイルを作成し、まず計画を提示してください」と依頼した場合は、計画を提示して止まる。「この計画で進めてください」のような返答を得た後に、その承認発言と提示した計画を対応づけて保存し、作業を始める。
- この順序を実際に保証できるかは、Skill より優先されるクライアントの指示と実行機能にも依存する。上位指示や実行機能が承認待ちを許さず、承認前の保存・委任・生成を避けられない場合、この Workflow は順序を強制できない。その制限を明示し、無条件に実行を待てるとは保証しない。
