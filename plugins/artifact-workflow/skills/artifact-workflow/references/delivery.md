# 成果物の引き渡し（Delivery）

Delivery は、全体検証を終えた成果物を利用者へ届けるために親が管理するフェーズである。作業タスクではなく、タスクIDを付けない。成果物の提示に加え、ユーザーが依頼した公開・提出・PR 作成などがあれば、対応する Skill や後続処理へ接続する。

## 計画で決めること

- 成果物の提示方法と、依頼された後続操作がある場合の担当 Skill・引き渡し先を、作業タスクとは別の Delivery 欄に記載する。
- 後続操作の依頼がなければ、完成した成果物またはアクセスできる参照先の提示をもって Delivery とする。公開や PR 作成を自動的に追加しない。
- 成果物の仕様に影響する引き渡し先や制約の不明点は、タスク計画時に確認する。後続操作だけに必要な情報の不足は、その操作の前に解消する。

## 外部 Skill との責務の境界

例えば「artifact-workflow でウェブサイトを作成し、その後 GitHub 操作 Skill で PR を作成する」という依頼では、ウェブサイトの作成・修正だけを作業タスクにする。親が品質確認を終えたら、完成した成果物の参照先・変更内容・検証結果・ユーザーが指定した PR の条件を GitHub 操作 Skill へ渡す。

GitHub 操作 Skill が PR 作成の具体的な操作を担う。この Workflow はその内部手順を作業タスクへ分解せず、引き渡しと結果の提示を管理する。Sites の公開や資料の提出でも、同じように対応する Skill・成果物種別の手順に従う。外部 Skill が要求する確認や処理を省略するという意味ではない。

利用する Skill は、ユーザーの指定と実際の利用可否に基づいて選ぶ。渡すのは検証済みの成果物と後続操作に必要な情報であり、タスク計画全体を公開・PR 作成の作業一覧へ展開し直さない。外部 Skill への引き渡しも親が管理し、この工程専用の `artifact-worker` は追加しない。

## 引き渡しと結果の提示

1. タスクと全体の検証を通過した成果物を用意し、計画に記載した提示方法・担当・引き渡し先を確認する。
2. 後続操作の依頼があれば、既存のユーザー指示と承認の範囲で担当 Skill・後続処理へ進む。同じ操作への承認を再度求めない。計画に書かれているだけで、依頼されていない公開・提出などへの許可を得たとは扱わない。
3. 完成した成果物または利用者がアクセスできる参照先と、タスクごと・全体の検証結果を簡潔に提示する。後続操作を行った場合は、返された公開先・PR などの参照先と実際の結果も添える。

必要な Skill・情報・権限がなく進められない場合や後続操作が失敗した場合は、成果物完成の状態と、Delivery の未完了項目・必要な対応を分けて伝える。確認できていない公開・提出・PR 作成を完了したと報告せず、依頼された操作を省略したまま依頼全体を完了扱いにしない。

引き渡し待ちを作業タスクへ変換したり、それだけで完成済みのタスクを未完了に戻したりしない。後続処理で成果物自体の不具合が判明した場合は、親が該当する元のタスクIDへ修正を戻し、影響するタスクと全体の条件を再検証してから Delivery を再開する。
