# コード生成

## 対象と役割

ソースコードまたはテストコードを新規に作成するタスク、あるいは既存コードを変更するタスクに適用する。親がこのモジュールを選んだときだけ使う。

このモジュールはコード成果物を作る順序を定める。言語・フレームワーク固有の実装規約、formatter・lint・静的解析の運用、細かな品質確認は定義しない。プロジェクトの指示と設定に従う。品質評価は生成後のレビュー工程で行う。

## 共通の進め方

1. 承認済みの計画、担当範囲、関連する既存コードとプロジェクトの開発・テスト手順を確認する。
2. 変更が必要な設計を具体化する。設計や必要な挙動が承認範囲から外れる場合は、実装前に親へ返す。
3. 以下の「既存コードの変更」または「新規実装」の順序で作業する。

## 既存コードの変更

1. 設計を確定し、変更対象と関連する既存 Unit Test を確認する。
2. 既存挙動を保証するテストが不足している場合、実装を変更する前に必要なテストを追加する。
3. 変更前の Unit Test を実行し、成功を確認して既存挙動を固定する。失敗した場合は実装変更に進まず、失敗したテスト・実行結果・原因の見立てを親へ返す。原因を解消し、失敗したテストと関連する Unit Test が通ったことを確認してから再開する。
4. 実装を変更する。
5. 設計変更で変わる挙動に対応するテストだけを修正・追加する。設計変更のない既存挙動に関するテストを、実装に合わせて書き換えない。
6. 関連する Unit Test を実行し、結果を確認する。

## 新規実装

1. 設計を確定する。
2. 実装する。
3. 仕様と主要な振る舞いを表す Unit Test を追加する。
4. 関連する Unit Test を実行し、結果を確認する。

## テスト失敗時の診断と再開条件

変更後の Unit Test が失敗した場合は、セルフレビューや親への完了報告に進まず、失敗内容を次のように切り分ける。

- 失敗が実装の不備を示す場合は、実装を修正し、失敗したテストと関連する Unit Test を再実行する。
- 失敗が承認済み設計で変更する挙動を検証するテストに限られ、実装が設計どおりの場合は、設計変更で変わる挙動に対応するテストだけを修正する。修正したテストと関連する Unit Test を再実行し、すべて通ったことを確認してから再開する。
- 失敗が変更範囲外、原因不明、または担当者だけでは解消できない場合は、テスト名・実行結果・原因の見立て・未解決点を親へ返して停止する。原因を解消し、失敗したテストと関連する Unit Test が通ったことを確認するまで再開しない。再開に計画やテスト範囲の判断が必要なら、親の判断を受けてから対応する。

失敗したテストを修正しただけで再開とはせず、修正後の再実行結果が通過していることを再開条件とする。失敗したテストを通過扱いにしたり、成功と報告したりしない。

## セルフレビューと親への返却

関連する Unit Test が通過した後に共通のセルフレビューを行う。セルフレビュー後、作成・変更した実物、実行したテストと結果、未実行の確認と理由を担当タスクIDに対応付けて親へ返す。

テストの実行方法はプロジェクトの指示と既存の仕組みに従う。必要なテストを実行できない場合は、未実行の範囲・理由・得られた結果を親へ返し、成功したものとして報告しない。
