# 親が管理する任意の相談

本 Workflow の親が、相談の必要性、呼び出し回数、実行枠、結果の採用、フォールバックを管理する。相談は生成ワーカーとは別の役割として扱い、作業タスクや必須のレビュー工程にはしない。

## 利用の判断と明示依頼

親が次のような具体的な阻害要因を確認して相談を検討する。利用候補は下記の手順で発見・読み込みし、未導入・無効なら通常フローを継続する。相談のためだけにインストールや環境変更を要求しない。

| 条件 | 親が確認する材料 |
| --- | --- |
| 設計が成立しない | 異なる2案が必須条件を満たせない結果、または必須条件同士の具体的な矛盾。 |
| セキュリティ対策を判断できない | 保護対象・信頼境界・具体的な問題経路と、対策の有効性が未確定な理由。危険な操作を試す必要はない。 |
| 変更の影響を確定できない | 依存先を調査しても残る共有契約・永続データ・複数担当への影響や、移行・復旧・検証の不確実性。 |
| 根拠が一致しない | 対象バージョンや条件を合わせても残る、一次資料・実測・実装の矛盾。 |
| 修正が停滞している | 異なる原因仮説による2通りの修正を検証しても残る失敗と、次の仮説を選べない理由。 |

通常の実装・定例レビュー、資料を読めば確認できる情報には相談を増やさない。ユーザーが特定の論点の相談を明示的に依頼した場合は、その依頼を優先する。

子ワーカーは、担当タスクID・問い・証拠・試した方法・残る阻害要因を親へ返す。親だけが相談 Skill と相談役を起動し、子は直接起動しない。親は下記で本文と契約を読んだ後、利用する Skill の名前・相談ID・1件の問いを今回の明示依頼として記録する。一般的な「任意で相談できる」という記述や子の依頼だけを起動命令にしない。

## 相談 Skill の発見・読み込み

`expert-escalation` は `allow_implicit_invocation: true` により通常のモデル向け一覧から発見できる。相談の開始条件は Skill の description と本文に定めるユーザーまたは親の明示依頼に限る。`artifact-workflow` だけが指定された新規タスクでも、親は次の手順を使う。

1. 現在のタスクに提示された利用可能な Skill 一覧を確認する。client の正式な一覧機能を使う場合も、現在のタスクの設定が反映された一覧に限る。
2. 名前が `expert-escalation` または Plugin 修飾名 `expert-escalation:expert-escalation` で、利用可能として提示された候補を確認する。有効状態が示される一覧では `enabled: true` だけを対象にする。複数ある場合は一覧の配布元・実際のパスとユーザーの指定を照合し、一意に決められなければ相談を見送る。先頭や最新らしいパスを推測で選ばない。
3. 一覧で示された実際のパスにある `SKILL.md` を読み、その本文から必要な参照資料を読む。発見・読み込みだけでは相談役を起動しない。親が今回の利用を明示的に決め、回数・入力・役割・枠を確認してから起動する。応答に `$expert-escalation` と書くだけでは本文の読み込みにならない。
4. 候補なし・無効・一覧取得不能・本文の読み込みエラー・候補が曖昧な場合は、理由を記録して下記のフォールバックへ進む。いずれも起動試行なし、消費0回。キャッシュの総当たりや別バージョンへの差し替え、Skill の有効化は行わない。

発見・読み込みに Python や Codex CLI の追加起動は不要。現在のタスクと設定が異なり得る別の App Server を起動して一覧を取得しない。他の client でも、その client が現在のタスクに提供する正式な一覧・読み込み機能を使う。

## 親と返却先の識別

親は現在の作業全体を担当するエージェントのままとし、識別のために別の親役割や固定のモデル名を追加しない。client が提供する親のエージェントIDまたはタスクの正規名を記録し、表示名は補助として添えられる。取得できない場合は生成作業IDとその作業内で一意な親ラベルの組を使い、実際の依頼元と対応付ける。

委任時にその親識別子と元の担当・タスクIDを渡し、相談依頼、相談結果、再開情報にも同じ識別子を引き継ぐ。相談IDで各依頼を区別する。識別子は照合と返却のための情報であり、名前に「親」を付けただけで起動権限を得るものではない。実際の委任関係と最上位の親からの明示依頼を確認する。

## 回数の上限と記録

本 Workflow による自律的な相談は、**現在の生成作業の開始・再開から、ユーザーへの確認で実際に作業を中断するまでの区間で合計最大3回**とする。親が全ワーカー・全論点・全相談役の試行を1つの記録に集約する。ワーカー人数や生成・修正の回数とは別に管理し、各ワーカーへ相談回数を配分しない。

ユーザーが追加相談や別の上限を明示指定した場合は、親がその指定範囲を記録して優先する。単独の `expert-escalation` 呼び出しに本 Workflow の上限を持ち込まない。

記録は親の会話または既存の作業記録に保持し、Plugin のインストール先へ保存しない。

```text
生成作業ID / 区間ID / 親識別子（任意で表示名）/ 区間の開始・再開の根拠
区間内の使用回数 / 上限（既定3）/ ユーザーによる変更指定があればその範囲
進行中の相談ID / 実行ID / 実行状態
試行履歴: 相談ID / 元の担当・タスクID / 問い・証拠 / 役割 /
          起動試行の有無 / 結果の状態・参照先 / 採否・検証結果
継続・停止の対象と理由 / 未解決の条件 / ワーカーの再開情報
```

1. 起動前に、記録の継続性、残る回数、役割・入力・実行枠を確認する。使用回数が不明なら新規相談を止めて記録を回収し、0から始めない。
2. 親が相談IDを付け、実際に起動または追加回答の生成を試す直前に1回を確保して記録する。事前確認だけで終われば使用回数は増やさない。
3. 起動を試した後のエラー、タイムアウト、キャンセル、結果未取得、実行有無が不明な場合も1回として記録し、戻さない。結果を元の担当の採否・検証結果と対応付ける。
4. 同じ相談役への追加質問・再実行・役割変更も新たな1回。待機・状態照会・同じ実行の結果回収だけなら追加しない。再相談には前の助言・検証結果と、判断を変え得る証拠・修正案・未回答の問いを添える。

相談は直列に行い、未完了の相談を同時に2件持たない。タイムアウト時も既存の実行IDの完了・停止を確認してから次を起動する。実行状態が不明なら新規相談を止め、状態確認と相談に依存しない作業を続ける。

## 相談用の同時起動枠

`artifact-worker` は同時に最大3人、相談役は同時に1人を別々に管理する。ただし client の実行枠が共通なら、両者の合計が実際の枠に収まるようにする。相談役を生成ワーカーとして数えたり、相談役へ生成を任せたりしない。

利用可能な子エージェント枠から他の実行が使う分を除いた枠数を確認する。相談を併用し、2枠以上ある場合は、生成を委任する前に相談用の1枠を予約し、生成ワーカーを残りの範囲で最大3人にする。例えば子枠が3つならワーカー2人＋相談用1枠、4つならワーカー3人＋相談用1枠とする。

1枠しかない場合、または既存の担当がすべての枠を占有している場合は、次の順で交代する。

1. 親は新たなワーカー起動を止め、交代する担当へ、成果物の保存と相談依頼・再開情報の返却を指示する。返却にはタスクID、編集範囲、成果物・ログの参照先、実行中の処理、未充足条件、試した方法、再開位置を含める。
2. 担当は相談に依存する作業を止め、返却してその実行を終える。親は返却と状態を確認し、書き込み中の処理が残る場合は安全に停止・完了するまで状態を回収する。
3. 親は client が提供する停止・終了・枠解放の手段を使い、実際に空き枠ができたことを確認する。返答済み・待機中だけで解放されたとみなさない。解放を確認できないなら、枠不足として相談を見送り、下記のフォールバックを選ぶ。
4. 空いた枠で相談を起動し、結果回収後に相談役の終了・枠解放を確認する。その後、同じタスクID・承認範囲・保存済み成果物・再開情報と助言を `artifact-worker` へ渡して再開する。client が再開に対応するなら既存の担当を再開し、そうでなければ新しい担当へ同じ情報を渡す。

全ワーカーが相談待ちのときは、全員のタスク完了を待つ処理に入らず、返却・枠解放を行う。子の返却はタスク完了の宣言ではない。相談できない環境でも、親は `artifact-worker` による生成と通常の検証の責任を維持する。

## 結果に応じたフォールバック

`expert-escalation` では `attempted` と `execution_state` を回数・状態の判断に使う。他の相談手段でも同等の事実を記録する。

| 状況 | 親の記録と対応 |
| --- | --- |
| 未導入・無効 | 起動せず消費0回。通常フローを継続する。 |
| 発見・読み込み不能・候補が曖昧・役割未登録・枠不足 | `unavailable`、起動試行なし、消費0回。自力での判断を含む通常フローへ戻すか、阻害要因が残る作業だけを止める。 |
| 入力不足 | `input_insufficient`。起動前なら0回、起動後の回答なら1回。入手できる入力は親が補う。 |
| 起動失敗・結果未取得 | `no_result`、起動を試した1回を記録する。助言取得やレビュー成功として扱わず、未完了の実行は回収・停止を管理する。 |
| 助言取得 | 元の担当が採否・実装・必要な検証を行い、親が通常の完了条件で判断する。 |
| 上限到達 | 親が追加相談を止める。得られた助言の検証と残る作業の継続可否を判断する。 |
| 有効な次の案がない・人間判断が必要 | 未解決の条件と影響範囲を整理し、必要な情報・判断だけをユーザーへ確認する。 |

上限到達や相談不能だけでは全体を止めない。親が、自力での継続、該当作業と依存先だけの停止、全体停止から選び、理由を記録する。全体の必須条件に阻害要因が及び、残る作業も進められない場合に全体停止を選ぶ。相談上限を使い切るための追加相談はしない。

停止する場合は親が対象の担当へ範囲を伝え、成果物・ログ・進行中の実行状態を保全する。ユーザーへの確認には、完了・未完了の範囲、試した内容と結果、残る条件、選択肢・推奨・必要な判断を示す。部分的な成果物を全体完了として渡さない。

## 再開とフロー終了

ユーザーへの確認で実際に作業を中断した後、返答を受けて再開するときに、親が新しい区間IDと使用回数0の記録を作る。以前の履歴、未解決の条件、未完了の実行状態を引き継ぐ。通常の確認による中断も同様に扱う。

進捗コメント、作業を続けながらの非同期質問、部分停止、子の返却、担当交代、論点の分割、要約・引き継ぎだけでは回数を戻さない。枠を戻すためだけの中断・自動再開は行わない。ユーザーの返答は不足する権限や未回答の必須条件の代わりにはならない。

本 Workflow の終了後はこの上限を後続処理へ持ち越さず、後続処理の親が自分の方針を管理する。ただし、相談履歴と未完了の実行状態は[引き渡し情報](delivery.md)に含め、境界を越えた重複起動を避ける。
