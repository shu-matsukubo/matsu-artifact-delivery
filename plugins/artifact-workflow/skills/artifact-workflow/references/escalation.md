# 任意相談の管理

相談の必要性・起動・回数・枠・助言の採否・フォールバックは親が管理する。相談は任意で、生成タスクやレビュー工程にしない。

## 起動条件

- 具体的な設計矛盾、未解決のセキュリティ判断、共有契約/移行/復旧の影響不確実性、一次資料と実測の矛盾、異なる原因による2回の修正失敗を確認した場合に検討する。
- 通常の実装・定例レビュー・資料から解決できる疑問に相談を増やさない。相談のためだけにインストールや環境変更を要求しない。ユーザーが論点を明示指定した場合は優先する。
- 子はタスクID・問い・証拠・試行・阻害要因・再開情報を親へ返す。reviewer はレビューID・指摘ID・対象版も含める。親だけが Skill/相談役を起動する。
- reviewer の依頼では発見元 reviewer と修正 worker を区別し、reviewer の編集禁止を伝える。結果後、修正はワーカー、独立再レビューはレビュワー、採否・完了検証は親が行う。

## 発見・起動

1. 現在のタスクに提示された利用可能 Skill 一覧を確認する。正式な一覧機能を使う場合も現在タスクの設定を反映したものに限る。
2. `expert-escalation` または `expert-escalation:expert-escalation` の利用可能な候補を選ぶ。有効状態がある場合は `enabled: true` に限る。複数候補は配布元・実パス・ユーザー指定で一意に特定し、曖昧なら起動しない。
3. 実際のパスの `SKILL.md` と必要な参照資料を読む。親が今回の相談を明示決定し、入力・回数・枠を確認後、`references/advisor-contract.md` を含めて標準 subagent を1件起動する。
4. 候補なし/無効/一覧取得不能/読み込みエラー/曖昧なら理由を記録して通常フローへ戻る。起動試行なし、消費0回。キャッシュ総当たり、別版への置換、有効化、別 App Server 起動をしない。

## 入力・返却契約

親は正規の agent ID またはタスク名を識別子として記録する。取得不能なら生成作業IDと一意な親ラベルを組み合わせる。表示名だけで親権限を推定しない。委任、相談依頼、結果、再開に親識別子・元担当・タスクID・相談IDを引き継ぐ。

記録には生成作業ID・区間ID・親識別子・区間根拠、使用数/上限、相談ID・実行ID・状態、元担当/タスクID、問い/証拠、起動試行、結果参照、採否/検証、停止範囲と理由、再開情報を含める。会話または既存の作業記録に置き、Plugin インストール先へ保存しない。

## 回数・同時実行

- 現在の生成作業の開始/再開から、ユーザー確認で実際に中断するまでに合計最大3回。全担当・論点・相談役の試行を親が1記録へ集約し、相談役は1役に固定する。ユーザー指定の別上限は指定範囲で優先する。単独 Skill 呼び出しへこの上限を適用しない。
- 同じ相談役への再相談は新しい1回。前の助言・検証結果と、判断を変え得る新証拠・修正案・未回答の問いを添える。実際に起動または追加回答を試す直前に1回記録する。起動後のエラー、タイムアウト、キャンセル、結果未取得、起動有無不明も消費扱い。事前確認のみは消費しない。同一実行の待機・状態照会・結果回収は追加しない。追加質問・再実行・役割変更は各1回。
- 相談は直列。進行中1件の終了/停止が確認できるまで次を起動しない。使用回数不明なら記録を回収し、0から再開しない。
- worker 最大3人、reviewer 最大1人、相談役最大1人。別々に数えるが client 枠が共通なら合計を実枠内にする。相談役を worker/reviewer として数えず、生成やレビューを代行させない。相談併用かつ子枠2以上なら生成委任前に相談用1枠を予約し、worker は残り枠内にする。reviewer 実行分も控除する。

## 枠の交代と再開

- 相談枠がない場合、親は新規 worker 起動を止め、担当へ成果物保存・問い/証拠・ログ・未充足条件・実行中処理・試行・再開位置の返却を指示する。
- 担当は相談依存作業を止めて返却し、実行を終える。reviewer も確認済み項目・指摘・未確認事項を返す。親は書込処理を安全に停止/完了し、client の終了手段で実際の枠解放を確認する。返答済み・待機中だけで解放と見なさない。
- 空いた枠で相談し、結果後に相談役の終了・枠解放を確認する。同じタスクID・承認範囲・成果物・再開情報と助言を元の役割へ返す。既存担当を再開できなければ同情報で新担当を起動する。
- 全workerが相談待ちなら全員完了を待たず回収・枠解放する。返却はタスク完了を意味しない。相談不能でも親は生成と通常検証を維持する。

## 結果とフォールバック

`expert-escalation` の `attempted` と `execution_state`（他手段も同等の実行事実）で状態を判断する。

| 状況 | 記録と対応 |
| --- | --- |
| 未導入・無効 | 起動せず消費0回。通常フローを継続する。 |
| 発見/読み込み不能、候補曖昧、起動手段なし、枠不足 | `unavailable`、起動試行なし、0回。通常継続または阻害対象だけ停止。 |
| 入力不足 | `input_insufficient`。起動前0回、起動後1回。親が入手可能な入力を補う。 |
| 起動失敗・結果未取得 | `no_result`、1回。助言やレビュー成功と扱わず実行を回収/停止する。 |
| 助言取得 | 生成・修正はワーカー、独立再レビューはレビュワーへ戻す。各担当が助言を検証し、採否と完了条件は親が判断。 |
| 上限到達 | 追加起動せず助言を検証し、継続可否を判断。 |

上限到達や相談不能だけでは全体を止めない。親は自力継続・阻害作業と依存先だけ停止・全体停止を選び理由を記録する。全必須条件が阻害され残作業も進められない時だけ全体停止する。上限消費目的の起動はしない。

停止時は担当・成果物・ログ・実行状態を保全し、ユーザーには完了範囲、試行と結果、残る条件、必要な判断を示す。部分成果を全体完了として渡さない。

## 中断と終了

ユーザー確認で実際に中断した後、返答を得て再開する場合は新しい区間ID・使用数0で記録し、履歴・阻害条件・実行状態を引き継ぐ。進捗質問、作業継続中の非同期質問、部分停止、担当交代、論点分割、要約だけではリセットしない。枠解放目的の中断・自動再開は禁止。ユーザー返答は権限や必須条件の代わりにならない。

Workflow 終了後は上限を後続処理へ持ち越さない。相談履歴と未完了実行状態は[引き渡し](delivery.md)に含め、重複起動を避ける。
