# タスク分解の方針

成果物を完成させるために必要な作業へ分解する。特定の開発工程や成果物形式を当てはめず、依頼の目的と必要な結果からタスクを決める。

## 作業タスクに含めるもの

タスクIDを付けるのは、作業者が成果物そのものを作成・変更する作業だけとする。機能実装、表示や操作性の調整、永続化、文章や資料の作成など、完成に必要な内容で分ける。

次の二つは作業タスクから除外する。

- **品質・完了処理**：セルフレビュー、動作検証、完了条件の確認、全体検証。各タスクの処理または成果物全体の処理として計画に記載し、独立したタスクIDを付けない。
- **Delivery**：完成した成果物の提示、公開、提出、PR 作成、外部 Skill への引き渡し。[引き渡しの方針](delivery.md)に従い、タスク外の Delivery 欄に方法と担当を記載する。外部 Skill の内部手順は分解しない。

工程を別の名前にして作業タスクへ残したり、「公開済み」「PR が作成されている」を作成タスクや全体の完了条件へ入れたりしない。完成した成果物の状態と、Delivery で確認する結果を分ける。

テストコードや検証報告書そのものが依頼された成果物なら、その作成・変更は作業タスクにできる。成果物を確認する行為や、この Workflow のレビュー記録を作るだけの処理とは区別する。

## 分解する粒度

- 最終的に作るもの、用途、作業範囲、制約を確認する。計画の判断に影響する不明点はユーザーへ確認し、前提があれば計画に明記する。
- 各タスクを実行可能で、後工程で結果を検証できる大きさにする。小さな操作ごとに分割するなど、必要以上に細かくしない。
- タスク数は必要な作業量に合わせる。一つの成果物の一部分を扱うタスクや、複数のタスクで一つの成果物を完成させる構成でもよい。
- 実行順に影響する依存関係がある場合のみ、計画に補足する。

## 分解例

以下のタスク数は例であり、実際には必要な作業量に合わせる。

| 依頼 | 作業タスク | タスク外で扱う処理 |
| --- | --- | --- |
| ウェブサイトを作成後、GitHub 操作 Skill で PR を作成する | T1: ウェブサイトを作成する | T1 のセルフレビュー・検証と全体検証を経て、Delivery で完成した成果物を GitHub 操作 Skill へ渡す。PR 作成は同 Skill が担う。 |
| Sites でサイトを作成して公開する | T1: サイトを作成する | 品質確認後、Delivery で Sites の公開手順に従う。「T2: Sites で公開」は作らない。 |
| 入力フォームと入力内容の保存機能を作成する | T1: フォームを実装する、T2: 永続化を実装する | 各タスクを確認し、入力から保存・再表示までを全体検証する。「T3: セルフレビューと動作検証」は作らない。 |
| 既存システムの検証報告書を作成する | T1: 調査・検証結果をまとめた報告書を作成する | 報告書自体のセルフレビューと完了条件の検証を行い、Delivery で報告書を提示する。 |

## 各タスクに必要な情報

| 項目 | 記載する内容 |
| --- | --- |
| タスクID | `T1`、`T2`、`T3` のような一意な識別子。 |
| タスク名 | 何を行うかが分かる短い名前。 |
| 目的 | この作業が成果物の完成に必要な理由。 |
| 成果物 | 何を作れば完了なのか。ファイル全体、一部分、その他の確認可能な結果などを具体化する。 |
| 完了条件 | 実際の成果物を見て充足を判断できる条件。確認対象と判断基準を明確にする。 |

「適切に作る」「品質を高める」だけでは完了条件にしない。必要な内容、満たすべき制約、期待する状態などを確認できる表現にする。

タスクIDは表示順とは独立した識別子として、生成・セルフレビュー・検証で同じタスクを参照するために使う。並べ替えてもIDを変更せず、削除したタスクのIDを別のタスクへ再利用しない。

## 計画の提示

[タスク計画テンプレート](../assets/task-plan-template.md)を使い、必要な数のタスクを記入してユーザーへ提示する。テンプレートの記入案内は取り除き、目的・成果物・完了条件をユーザーが判断できる状態にする。

提示前に、各タスクに成果物を作成・変更する内容があること、品質確認と Delivery が独立タスクや作成の完了条件へ混ざっていないことを確認する。混ざっていれば、それぞれ品質確認の進め方または Delivery 欄へ移す。承認済み計画でこの混在が見つかった場合も、親が [SKILL.md](../SKILL.md) の計画変更ルールに従って整理してから該当作業を委任する。

全体の完了条件には、組み合わせた成果物が依頼の目的を満たす状態を記載する。Delivery 欄にはユーザーへの提示方法と、依頼された後続操作がある場合の担当 Skill・引き渡し先・必要な前提を記載する。後続操作の依頼がなければ成果物の提示だけでよい。

承認後も、承認された計画を会話内または作業場所で参照できる状態に保つ。後工程ではこの計画を基準にし、完了条件を成果物に合わせて書き換えない。
