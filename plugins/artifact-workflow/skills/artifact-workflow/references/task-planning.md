# タスク分解の方針

今回の生成範囲の成果物を完成させるために必要な作業へ分解する。特定の開発工程や成果物形式を当てはめず、依頼のうち本 Workflow が担当する目的と必要な結果からタスクを決める。

## 今回の生成範囲を決める

親が依頼全体から、本 Workflow で生成・検証する成果物と、終了後に選択した手段で続行する処理を分ける。後続処理の担当側で行う作成・編集・実行・検証は生成タスクへ取り込まず、その担当範囲をワーカーの編集対象にしない。

後続処理の結果が必要な成果物は、必要な入力を得た後に親が別の生成として扱う。今回の計画にはその結果を待たずに完成・検証できる成果物を含め、後で行う依頼は引き渡し情報に残す。未確定の値で成果物を完成扱いにしたり、後続の依頼を省略したりしない。入力が得られた後に本 Skill を改めて使う場合は、その生成範囲の計画に対して既存の承認ルールを適用する。

完成済みの成果物の提出など、依頼が後続処理だけなら、本 Workflow の計画やワーカーを用意せず、親が選択した手段で進める。

## 作業タスクに含めるもの

タスクIDを付けるのは、作業者が成果物そのものを作成・変更する作業だけとする。機能実装、表示や操作性の調整、永続化、文章や資料の作成など、完成に必要な内容で分ける。

次の項目は作業タスクから除外する。

- **品質・完了処理**：セルフレビュー、独立レビュー、動作検証、完了条件の確認、全体検証。各タスクの処理または成果物全体の処理として計画に記載し、独立したタスクIDを付けない。
- **成果物の提示・引き渡し**：[引き渡しの方針](delivery.md)に従い、タスク外の Delivery 欄に完成品の参照方法と親へ渡す情報を記載する。
- **後続処理**：更新・公開・提出などの実行と、その検証・成功判定。本 Workflow の計画には含めず、親が続行する依頼として Delivery 欄に概要を残す。

工程を別の名前にして作業タスクへ残したり、「公開済み」「提出先で受理済み」を作成タスクや全体の完了条件へ入れたりしない。今回の成果物の完成と、フロー終了後の結果を分ける。すでに得られた結果を入力に成果物を作る場合は、その入力が成果物に正しく反映されていることを完了条件にできる。

テストコードや検証報告書そのものが依頼された成果物なら、その作成・変更は作業タスクにできる。成果物を確認する行為や、この Workflow のレビュー記録を作るだけの処理とは区別する。

## 分解する粒度

- 今回の生成で作るもの、用途、作業範囲、制約を確認する。計画の判断に影響する不明点はユーザーへ確認し、前提があれば計画に明記する。
- 各タスクを実行可能で、後工程で結果を検証できる大きさにする。小さな操作ごとに分割するなど、必要以上に細かくしない。
- タスク数は必要な作業量に合わせる。一つの成果物の一部分を扱うタスクや、複数のタスクで一つの成果物を完成させる構成でもよい。
- 実行順に影響する依存関係がある場合のみ、計画に補足する。

## 分解例

以下のタスク数は例であり、実際には必要な作業量に合わせる。

| 依頼 | 今回の生成タスク | 品質確認とフロー終了後の扱い |
| --- | --- | --- |
| 調査レポートを作成し、指定先へ提出する | T1: 調査レポートを作成する | レポートの検証と引き渡しで生成フローを終了する。親が指定された手段で提出・確認を続行する。 |
| アプリを作成し、指定の手段で公開する | T1: 引き渡すアプリ成果物を作成する | アプリの検証と引き渡しで生成フローを終了する。公開に伴う作成・編集・実行・検証は、親が指定された手段の手順で続行する。 |
| 成果物を提出し、発行された受付番号を記載した記録も作る | T1: 提出する成果物を作成する | 成果物の検証と引き渡しで生成フローを終了する。親が提出して受付番号を得た後に、記録を別の生成として作る。記録作成の依頼と必要な入力は引き渡し情報に残す。 |
| 完成済みの資料を指定先へ提出する | 本 Workflow の生成タスクなし | 本 Workflow を適用せず、親が指定された手段で提出・確認を行う。 |
| 入力フォームと入力内容の保存機能を作成する | T1: フォームを実装する、T2: 永続化を実装する | 各タスクを確認し、入力から保存・再表示までを全体検証する。「T3: セルフレビューと動作検証」は作らない。 |
| 既存システムの検証報告書を作成する | T1: 調査・検証結果をまとめた報告書を作成する | 報告書自体のセルフレビューとタスク・全体の完了条件の検証を行い、完成品を提示してフローを終了する。 |

## 各タスクに必要な情報

| 項目 | 記載する内容 |
| --- | --- |
| タスクID | `T1`、`T2`、`T3` のような一意な識別子。 |
| タスク名 | 何を行うかが分かる短い名前。 |
| 目的 | この作業が成果物の完成に必要な理由。 |
| 成果物 | 何を作れば完了なのか。ファイル全体、一部分、その他の確認可能な結果などを具体化する。 |
| 完了条件 | 実際の成果物を見て充足を判断できる条件。確認対象と判断基準を明確にする。 |

「適切に作る」「品質を高める」だけでは完了条件にしない。必要な内容、満たすべき制約、期待する状態などを確認できる表現にする。

タスクIDは表示順とは独立した識別子として、生成・セルフレビュー・独立レビュー・検証で同じタスクを参照するために使う。並べ替えてもIDを変更せず、削除したタスクのIDを別のタスクへ再利用しない。

## 計画の提示

[タスク計画テンプレート](../assets/task-plan-template.md)を使い、必要な数のタスクを記入してユーザーへ提示する。テンプレートの記入案内は取り除き、目的・成果物・完了条件をユーザーが判断できる状態にする。

提示前に、各タスクが今回の生成範囲に属し、後続処理の結果を待たずに完了を検証できることを確認する。品質確認を独立タスクにせず、後続処理の実行・検証をタスクや全体の完了条件へ混ぜない。品質確認は進め方として記載し、後続の依頼は引き渡し情報へ移す。承認済み計画でこの混在が見つかった場合も、親が [SKILL.md](../SKILL.md) の計画変更ルールに従って整理してから該当作業を委任する。

全体の完了条件には、今回の成果物を組み合わせたときに、合意した生成目的を満たす状態を記載する。Delivery 欄には成果物の参照方法と親へ渡す情報、依頼された後続処理の概要、結果を得た後に行う依頼を記載する。後続処理の実行手順や検証条件は定義しない。後続の依頼がなければ成果物の提示だけでよい。

承認後は、合意済み計画をMCPへ保存し、保存成功を確認してから生成へ進む。以後の計画参照の正本はMCPの保存済み計画とし、後工程では取得した計画を基準にする。完了条件を成果物に合わせて書き換えない。保存・取得・更新・完了記録の手順と失敗時の扱いは[タスク計画の一時保持](task-memory.md)を参照する。
