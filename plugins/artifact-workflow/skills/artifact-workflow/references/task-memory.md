# 合意済みタスク計画の一時保持

`artifact-task-memory` MCP は、今回の生成フローで合意した計画をJSONの最新スナップショットとして保持する。会話の検討経緯ではなく、保存済み計画を生成・委任・検証の参照元にする。MCPは保存・取得・明示的な初期化・親によるフロー完了の記録・明示的な回収を行う。承認・完了の判断、タスク進捗の自動管理、Git操作、成果物本体の保存は行わない。

## セッションと初期化

- **新しい生成フローの計画を始める前に一度だけ**、親がUUIDを `sessionId` として発行し、`initialize_session({sessionId})` を呼ぶ。同じフローの全工程でそのIDを使う。会話やスレッドの識別子は保存キーに使わない。未作成のIDだけを初期化し、既存の計画と他のセッションには触れない。`SESSION_EXISTS` なら既存計画を保全し、必ず別のUUIDを発行して初期化をやり直す。`get_plan` による続行は同一フローの明確な続行に限る。使用したIDは作業記録と引き継ぎ要約に残し、委任先にも渡す。許容文字は英数字・`_`・`-`、長さは1〜128文字。
- 作業の続行、会話の短縮、MCP再接続、ワーカー起動は新しいフローではない。これらでは初期化せず、引き継いだ同じIDで `get_plan` を呼ぶ。MCPプロセスの起動にも自動削除を持たせない。
- 同じフローの親・ワーカー・レビュワーは同じ `sessionId` を使う。委任先自身のIDや別フローのIDに置き換えない。並列の独立したフローには異なるIDを割り当てる。
- IDが不明な場合は、以前渡された識別子を確認してから続ける。別IDのデータを推測して取得したり、続行のつもりで新しいIDを発行したりしない。

## 保存・参照・書き戻し

| 操作 | 入力 | 結果 |
| --- | --- | --- |
| `initialize_session` | `sessionId` | 親が新規フローの開始時に未作成のセッションだけを作成する。既存セッションは変更せず `SESSION_EXISTS` を返す。 |
| `reset_session` | `sessionId` | 親が利用者から対象計画の置換について明示的に許可を得た場合に限り、指定IDだけを空にする。 |
| `collect_completed_sessions` | なし | 親が利用者から完了済み計画の回収について明示的に許可を得た場合に限り、保存先内の完了記録済みセッションを回収する。 |
| `get_plan` | `sessionId` | 保存済みの全計画・`revision`・`completedAt` を返す。未初期化または削除済みなら `session: null`。 |
| `save_plan` | `sessionId`, `expectedRevision`, `plan` | 最新の版を確認して未完了の計画全体をJSONへ保存・置換し、新しい `revision` を返す。 |
| `complete_session` | `sessionId`, `expectedRevision` | 最新の版を確認してフロー完了を記録し、`completedAt` と新しい `revision` を含む `session` を返す。 |

1. 未承認の計画案は会話上で整理する。親がユーザーの承認、または今回の範囲について明示された承認手続き省略を確認してから、合意済み計画全体を `save_plan` で保存する。`expectedRevision` は通常 `initialize_session` または `get_plan` で返された最新の値を使う。`reset_session` は明示的に許可された既存計画の置換にだけ使い、新規フローの開始手順にはしない。
2. 生成・委任・検証・続行の前に `get_plan` で読み、保存済みの要求・制約・タスクID・完了条件・承認根拠を参照する。委任先には親の `sessionId` と担当タスクIDを渡す。ワーカーやレビュワーからMCPを参照できない環境では、親が取得した最新スナップショットを渡す。
3. 計画の変更が必要なら、親が既存の承認ルールに沿って変更内容を確定させる。その後に最新の計画を読み、変更を反映した**計画全体**を書き戻す。配列のマージや部分更新はしない。省いたタスクは削除されるため、変更しない項目も含める。未確定な変更案で保存済み計画を置き換えない。
4. 初期化・計画保存・完了記録・既存計画の置換・完了計画の回収は親だけが行う。ワーカーとレビュワーは `get_plan` だけを参照に使い、変更が必要なら親へ返す。`approval.mode` と `evidence` は親による判断の記録であり、MCPが実際のユーザー発言を照合したり承認を代行したりするものではない。

`session: null` は未初期化または削除済み、`plan: null` は承認済み計画が未保存であることを意味する。未完了の作業を続行する場合、保存失敗や欠落を成功とみなさず、既存の合意を確認して保存が成功してから生成を進める。未確定な会話を補完して計画扱いにしたり、リポジトリ内に代替のタスク管理ファイルを作ったりしない。完了後の修正は、旧計画の有無によらず後述の新しい修正タスクとして扱う。

## 計画のJSON

ユーザーへの提示には [タスク計画テンプレート](../assets/task-plan-template.md) を使う。保存時は、その合意済み内容を以下の形式へ対応付ける。`request` は元の依頼、`scope` は今回の生成範囲、`inputs` は作業に必要な入力の参照先。`tasks` は目的・成果物・完了条件と依存関係、`acceptanceCriteria` は全体の条件、`delivery` は引き渡し情報を記録する。空の要件・制約・入力・依存関係は空配列にする。

```json
{
  "request": "提供したCSVから月次レポートを作成してください。",
  "scope": "月次レポートの本文作成と検証まで。",
  "requirements": ["日本語で作成する"],
  "constraints": ["公開は今回の生成範囲に含めない"],
  "inputs": [{ "description": "入力CSV", "reference": "C:/inputs/month.csv" }],
  "tasks": [{
    "id": "T1",
    "description": "月次レポートを作成する",
    "purpose": "月次の状況を読み手へ伝える",
    "deliverable": "C:/outputs/report.md",
    "acceptanceCriteria": ["提供された集計値と本文が一致する"],
    "dependsOn": []
  }],
  "acceptanceCriteria": ["完成したレポートを利用者が参照できる"],
  "delivery": "完成品の絶対パスと検証結果を親へ返す。",
  "approval": {
    "mode": "approved",
    "evidence": "ユーザーが上記計画に『承認します』と回答。"
  }
}
```

承認手続きの省略を明示された場合は `mode: "waived"` とし、`evidence` に指示と適用範囲を記録する。承認待ちを表す値は保存できない。タスクIDは重複不可、依存先は計画内のタスクに限り、循環は不可。検証専用のタスクは追加しない。各タスクと全体の完了条件は少なくとも1件必要。

保存ファイルは上記 `plan` に、`schemaVersion: 1`、`sessionId`、競合検出用の `revision`、`createdAt`、`updatedAt`、`completedAt` を付けたオブジェクトになる。`completedAt` は未完了なら `null`、完了記録後はMCPが設定する日時で、計画そのものとは分けて保持する。旧形式のようにこの項目がない場合は `null` として読み、完了とは推測しない。会話を読み直さなくても計画から作業できるよう、必要な制約・入力・出力先を省略しない。タスクごとの進捗や作業履歴は自動復元せず、実施済み作業や成果物の現在の状態は実物を確認する。

## 保存場所と終了時の扱い

通常はクライアントが提供する `PLUGIN_DATA/task-memory/` に保存する。リポジトリやプラグインのソース配下には作業データを生成しない。直接起動時はOSの一時ディレクトリの `matsu-artifact-workflow/task-memory/` を使う。`ARTIFACT_WORKFLOW_DATA_DIR` で絶対パスを明示できるが、作業用リポジトリの外を指定する。

ファイル名は `sessionId` のSHA-256値に `.json` を付けたもの。Windowsでも大文字小文字の異なるIDや予約名が衝突しない。最新のJSONを一時ファイルから置換する。保存済み計画は1 MiB以内とし、成果物本体の代わりに参照先を記録する。

全タスクの完了、全体検証、完成品と検証結果の提示または引き渡しを終えたら、親が最新の `revision` で `complete_session` を呼び、成功を確認する。全タスク完了だけでは、全体検証や引き渡しが残っているため完了記録をしない。必要な情報を会話や後続処理へ渡し、保存済み計画を読み直さなくても続行できる状態にする。MCPは親の完了判断を記録し、成果物や検証結果を自動判定しない。未保存の計画は完了にできない。

完了した計画は、利用者が明示的に許可した回収または対象IDの置換まで読み取り専用で保存する。新しいフローの開始は他の完了済み計画を回収しない。`collect_completed_sessions` は保存先内の完了記録済みセッションだけを回収する。削除前には保存・初期化・完了記録と共通のセッション単位のロックを取得し、その時点の内容を検証する。ファイル名とIDが一致しないもの、破損・未対応形式、通常ファイルでないものは削除しない。ロック中や読み書きエラーのものも見送り、他の候補の処理を続ける。未完了セッション、成果物本体、無関係なファイルは削除しない。

`collect_completed_sessions` の `cleanup.deleted` は削除件数、`cleanup.skipped` は見送ったファイル名と理由コードの配列となる。ディレクトリ一覧の取得失敗は `file: "."` で返す。見送りがあっても他の候補の回収は完了しているため、理由を確認して必要な場合にだけ利用者へ再許可を求める。正常に読み取れた未完了セッションは保持され、見送り一覧には含めない。

保存先ディレクトリがまだない場合、`collect_completed_sessions` の `cleanup` は `{deleted: 0, skipped: []}` になる。完了記録のない旧形式や、完了を記録せず中断したデータも自動削除しない。履歴、一覧、TTL、別チャットからの復元機能は設けず、長期保存は保証しない。

## 後日の修正

完了後に修正が必要になったら、保存済み計画が残っていても終了済みフローを再開しない。親が現在の成果物と修正要求を確認し、新しい生成フローとして初期化して、修正範囲・成果物・完了条件を持つ修正タスクを計画する。既存の承認ルールに沿って合意した新しい計画を保存してから修正する。削除された計画の復元は前提にせず、元の要求が必要なら成果物・ユーザーの依頼など確認できる入力から整理する。必要な入力が不足していれば確認する。

## エラー時

- `REVISION_CONFLICT`：誰かが更新または初期化した。最新の `get_plan` と現在の合意を照合してから再保存する。古い内容の強制上書きや競合回避のための初期化はしない。
- `SESSION_BUSY`：同じセッションへの保存処理中。終了を待って再取得する。プロセスの強制終了でロックが残った場合は、自動で破壊せず、当該書き込みプロセスが終了済みであることを確認してからエラーに示された `.lock` だけを削除する。異なるセッションは利用を続けられる。
- `SESSION_COMPLETED`：終了済みの計画への保存。現在の成果物と修正要求を確認し、新しい修正タスクを計画する。
- `PLAN_NOT_SAVED`：計画未保存のまま完了を記録しようとした。合意済み計画の保存と作業・全体検証・引き渡しを確認する。
- `NOT_INITIALIZED`：未初期化または削除済みのセッション。後日の修正なら新しい生成フローから始める。
- `SESSION_EXISTS`：IDが既に使われている。既存セッションと計画を保全し、新規フローなら必ず別UUIDで `initialize_session` をやり直す。同一フローの明確な続行だけ同じIDで `get_plan` を使う。
- `INVALID_DATA`：JSONの破損やスキーマ不一致。保存内容を推測で補わず、内容を確認する。復旧のための `reset_session` は、利用者が対象計画の置換を明示的に許可した場合だけ行う。

MCPは同じOSユーザーによるローカル利用を前提とする。セッションIDは混線を防ぐ識別子であり、利用者間の認証やアクセス制御の境界ではない。
