# 合意済みタスク計画の一時保持

`artifact-task-memory` MCP は、今回の生成フローで合意した計画をJSONの最新スナップショットとして保持する。会話の検討経緯ではなく、保存済み計画を生成・委任・検証の参照元にする。MCPは保存・取得・置換・初期化のみを行い、承認判断、進捗の自動管理、Git操作、成果物本体の保存は行わない。

## セッションと初期化

- 親のチャット／スレッドの安定した識別子を `sessionId` に使う。取得できない場合は、親がUUIDを1つ生成してこのフローの識別子とする。使用したIDは開始時の作業記録と引き継ぎ要約に残し、委任先にも渡す。許容文字は英数字・`_`・`-`、長さは1〜128文字。
- **新しい生成フローの計画を始める前に一度だけ**、親が `reset_session({sessionId})` を呼ぶ。同じIDの以前の要求・タスク・承認記録をすべて初期化する。別のIDのデータは削除しない。
- 作業の続行、会話の短縮、MCP再接続、ワーカー起動は新しいフローではない。これらでは初期化せず、同じIDで `get_plan` を呼ぶ。MCPプロセスの起動にも自動削除を持たせない。
- 同じフローの親とワーカーは同じ `sessionId` を使う。ワーカー自身のIDや別フローのIDに置き換えない。並列の独立したフローには異なるIDを割り当てる。
- IDが不明な場合は、以前渡された識別子を確認してから続ける。別IDのデータを推測して取得したり、続行のつもりで新しいIDを発行したりしない。別チャットへの引き継ぎやID探索は保証しない。

## 保存・参照・書き戻し

| 操作 | 入力 | 結果 |
| --- | --- | --- |
| `reset_session` | `sessionId` | 指定セッションだけを空にし、`plan: null` と新しい `revision` を返す。 |
| `get_plan` | `sessionId` | 保存済みの全計画と `revision` を返す。未初期化なら `session: null`。 |
| `save_plan` | `sessionId`, `expectedRevision`, `plan` | 最新の版を確認して計画全体をJSONへ保存・置換し、新しい `revision` を返す。 |

1. 未承認の計画案は会話上で整理する。親がユーザーの承認、または今回の範囲について明示された承認手続き省略を確認してから、合意済み計画全体を `save_plan` で保存する。`expectedRevision` は直前の初期化または取得で返された値を使う。
2. 生成・委任・検証・続行の前に `get_plan` で読み、保存済みの要求・制約・タスクID・完了条件・承認根拠を参照する。委任先には親の `sessionId` と担当タスクIDを渡す。ワーカーからMCPを参照できない環境では、親が取得した最新スナップショットを渡す。
3. 計画の変更が必要なら、親が既存の承認ルールに沿って変更内容を確定させる。その後に最新の計画を読み、変更を反映した**計画全体**を書き戻す。配列のマージや部分更新はしない。省いたタスクは削除されるため、変更しない項目も含める。未確定な変更案で保存済み計画を置き換えない。
4. 初期化と保存は親だけが行う。ワーカーは計画を参照し、変更が必要なら親へ返す。`approval.mode` と `evidence` は親による判断の記録であり、MCPが実際のユーザー発言を照合したり承認を代行したりするものではない。

`session: null` や `plan: null` は、承認済み計画が未保存であることを意味する。保存失敗も成功とみなさない。既存の合意を確認して保存が成功してから、該当計画の生成を進める。未確定な会話を補完して計画扱いにしたり、リポジトリ内に代替のタスク管理ファイルを作ったりしない。

## 計画のJSON

ユーザーへの提示には従来の [タスク計画テンプレート](../assets/task-plan-template.md) を使う。保存時は、その合意済み内容を以下の形式へ対応付ける。`request` は元の依頼、`scope` は今回の生成範囲、`inputs` は作業に必要な入力の参照先。`tasks` は目的・成果物・完了条件と依存関係、`acceptanceCriteria` は全体の条件、`delivery` は引き渡し情報を記録する。空の要件・制約・入力・依存関係は空配列にする。

```json
{
  "request": "提供したCSVから月次レポートを作成してください。",
  "scope": "月次レポートの本文作成と検証まで。",
  "requirements": ["日本語で作成する"],
  "constraints": ["公開は今回の生成範囲に含めない"],
  "inputs": [{ "description": "入力CSV", "reference": "C:/inputs/month.csv" }],
  "tasks": [{
    "id": "T1",
    "description": "月次レポートを作成する",
    "purpose": "月次の状況を読み手へ伝える",
    "deliverable": "C:/outputs/report.md",
    "acceptanceCriteria": ["提供された集計値と本文が一致する"],
    "dependsOn": []
  }],
  "acceptanceCriteria": ["完成したレポートを利用者が参照できる"],
  "delivery": "完成品の絶対パスと検証結果を親へ返す。",
  "approval": {
    "mode": "approved",
    "evidence": "ユーザーが上記計画に『承認します』と回答。"
  }
}
```

承認手続きの省略を明示された場合は `mode: "waived"` とし、`evidence` に指示と適用範囲を記録する。承認待ちを表す値は保存できない。タスクIDは重複不可、依存先は計画内のタスクに限り、循環は不可。検証専用のタスクは追加しない。各タスクと全体の完了条件は少なくとも1件必要。

保存ファイルは上記 `plan` に、`schemaVersion: 1`、`sessionId`、競合検出用の `revision`、`createdAt`、`updatedAt` を付けたオブジェクトになる。会話を読み直さなくても計画から作業できるよう、必要な制約・入力・出力先を省略しない。実施済み作業や成果物の現在の状態は実物を確認する。作業履歴や完了状態の自動復元は初版の対象外。

## 保存場所と終了時の扱い

通常はクライアントが提供する `PLUGIN_DATA/task-memory/` に保存する。リポジトリやプラグインのソース配下には作業データを生成しない。直接起動時はOSの一時ディレクトリの `matsu-artifact-workflow/task-memory/` を使う。`ARTIFACT_WORKFLOW_DATA_DIR` で絶対パスを明示できるが、作業用リポジトリの外を指定する。

ファイル名は `sessionId` のSHA-256値に `.json` を付けたもの。Windowsでも大文字小文字の異なるIDや予約名が衝突しない。最新のJSONを一時ファイルから置換する。保存済み計画は1 MiB以内とし、成果物本体の代わりに参照先を記録する。

フロー完了時にはすぐに削除せず、同じセッションで次のフローを始めるときに全内容を初期化する。異なるIDのデータはその開始時にも削除しない。履歴、一覧、TTL、別チャットからの復元機能は設けず、長期保存は保証しない。

## エラー時

- `REVISION_CONFLICT`：誰かが更新または初期化した。最新の `get_plan` と現在の合意を照合してから再保存する。古い内容の強制上書きや競合回避のための初期化はしない。
- `SESSION_BUSY`：同じセッションへの保存処理中。終了を待って再取得する。プロセスの強制終了でロックが残った場合は、自動で破壊せず、当該書き込みプロセスが終了済みであることを確認してからエラーに示された `.lock` だけを削除する。異なるセッションは利用を続けられる。
- `INVALID_DATA`：JSONの破損やスキーマ不一致。保存内容を推測で補わない。計画を確認し、明示的に初期化して確定内容を再保存する。

MCPは同じOSユーザーによるローカル利用を前提とする。セッションIDは混線を防ぐ識別子であり、利用者間の認証やアクセス制御の境界ではない。
