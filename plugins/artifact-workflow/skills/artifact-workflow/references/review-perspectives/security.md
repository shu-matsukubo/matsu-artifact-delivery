# セキュリティ

`security` は、成果物の利用に伴う情報漏えい、権限の逸脱、意図しない操作を確認する特化観点。コードだけでなく、資料・データ・設定・エージェントの指示も対象になり得る。

## 適用条件と入力

秘密・個人情報、認証・認可、外部入力、ファイル／コマンド操作、外部への送信・公開の設定、エージェントの権限や信頼境界を含む場合、またはセキュリティが要求に明記されている場合に選ぶ。公開情報の体裁修正など、これらを扱わない成果物へ機械的に適用しない。

合意済みの用途・利用者・共有先、保護すべき情報や操作、入力元と出力先、実際のコード・設定・資料、利用可能な検証結果を参照する。不明な運用前提や資料は親へ返し、実物にない防御や権限を仮定しない。秘密の値そのものを新たに取得する必要はない。

## 確認する論点

該当する経路だけを次の観点で確かめる。各項目は `security` という1つの特化観点の内訳であり、すべてを実施する監査表ではない。

| 論点 | 確認内容と根拠の例 |
| --- | --- |
| 情報の扱い | 認証情報・個人情報・内部情報が、成果物本文、ログ、URL、添付・埋め込みデータ、資料のノートやメタデータへ不要に残らないか。想定する共有先に必要な情報だけが出るか。出力箇所と共有条件を根拠にする。 |
| 権限と信頼境界 | 想定利用者が必要な操作だけを行えるか。アクセス対象や操作の認可が適切な場所で行われ、表示を隠すだけの制御になっていないか。エージェントの起動・承認・外部操作が、依頼された担当の境界を越えないか。 |
| 外部入力の扱い | 入力からファイルパス・コマンド・クエリ・画面・外部リクエストへ至る経路で、意図しない実行・参照・送信が起きないか。エスケープや検証は実際の出力先に合うか。資料やツール出力の指示でエージェントの権限・役割が変わらないか。 |
| 副作用と失敗時の扱い | 書き込み・削除・公開・送信の対象範囲が限定され、失敗・再実行でも許可外の操作や情報露出を招かないか。成果物に含まれる設定や手順から判断し、後続の公開操作そのものは実行しない。 |

## 指摘と限界

[独立レビューの返却契約](../independent-review.md)に沿い、保護対象、問題のある箇所、入力元・操作主体から問題へ至る経路、成立条件と影響、根拠、推奨する修正・確認方法を親へ返す。脅威名や一般的なベストプラクティスの欠如だけで確定した問題にしない。報告に秘密値や個人情報を転記せず、位置やマスクした例で特定する。

読み取り専用の確認で分からないことは未確認として返す。攻撃・侵入テスト、実在の認証情報を使うアクセス、外部送信、依存関係の更新、設定変更は行わない。リポジトリ全体の網羅監査や、今回見ていない運用環境の安全性まで保証しない。

具体的な問題経路があるが対策の有効性を判断できない場合は、必要な前提・証拠・検討済みの案・判断を阻む理由を添えて親へ相談を依頼する。相談 Skill・相談役を直接呼ばず、親が利用判断と必要な検証を管理する。
