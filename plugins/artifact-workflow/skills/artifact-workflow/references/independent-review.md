# 独立レビューの方針

セルフレビューを終えた作業者の成果物を、生成・修正に関与していない `artifact-reviewer` が確認する。本 Workflow の標準工程として、親の完了条件の検証より前に行う。共通原則の見落としと該当する特化観点を確認し、修正は作業者、完了判定は親に任せる。

## 親による準備と委任

1. 親は生成開始前に `artifact-worker` と `artifact-reviewer` の両役割が利用可能か確認する。独立レビュワーは原則1人とし、同時に複数起動せず、観点ごとに増やさない。生成担当を同じ実行のままレビュワーへ切り替えない。
2. 親の `sessionId` で `get_plan` を読み、最新の合意済み計画、セルフレビュー済みの実物、対象タスクIDを対応付ける。複数タスクをまとめてレビューしてよいが、全成果物と組み合わせた状態を最終的に確認対象に含める。
3. [特化観点一覧](review-perspectives/index.md)から今回該当するものを**0〜3個**選ぶ。共通の[5原則](review-principles.md)は常に確認し、この上限には数えない。選定と呼び出しは親が管理し、承認済みの範囲内での観点選択にユーザーの追加承認を求めない。
4. レビューIDを付け、対象の版を特定する。コミットだけでは未コミット変更を識別できない場合、変更差分・ファイルのハッシュ・保存時点なども用いる。レビュー中は対象と関連する入力・依存物への編集を止め、指摘を実物に対応付けられる状態にする。
5. 登録済みの Custom Agent `artifact-reviewer` を指定し、次の入力だけで判断できる独立した実行へ委任する。可能なら生成担当の会話を継承しない。モデル・推論強度は役割定義に任せ、委任時に上書きしない。

渡す情報は、親識別子と `sessionId`、レビューIDと対象タスクID、承認済み計画と承認根拠、成果物・関連入力の参照先と対象の版、セルフレビュー結果、本資料、共通原則、選んだ特化観点のID・選定理由・資料とする。ファイルは絶対パスで渡す。MCPを参照できない担当には親が取得した最新の計画スナップショットを渡す。再レビューでは前回の指摘、親の採否と理由、修正内容・影響範囲も添える。

## 実行枠と独立性

生成ワーカーは同時に最大3人、独立レビュワーは同時に1人、任意の相談役は同時に1人として親が別々に管理する。client の枠を共有する場合は合計を実際の上限に収める。レビューのためにワーカーを増やさず、通常は生成・セルフレビューの返却後に交代する。

枠が足りない場合は、親が担当から成果物・記録・進行中の処理・再開情報を回収し、書き込みが止まり、client 上の枠が実際に解放されたことを確認してから交代する。待機中や返答済みというだけで枠が空いたと判断しない。手段がなく交代できない場合は未実施として扱う。相談へ交代する場合も[相談用の実行枠](escalation.md#相談用の同時起動枠)の手順に従い、再開先を元の役割に戻す。

レビュー対象を生成・修正したことのない同じレビュワーを再レビューに使ってよい。レビュー中に対象や関連部分が変わった場合は影響部分の結果を無効とし、親が変更後の版を渡して再レビューする。

## 確認と親への返却

レビュワーは読み取り専用で実物を確認する。書き込みを伴う検証が必要なら、その方法と必要な根拠を親へ返し、親が適切な担当で取得する。作業者への修正依頼、追加の観点選択、他のエージェント・相談 Skill の起動は行わない。

次を親へ簡潔に返す。別の報告書ファイルや、5原則ごとの定型チェック表は必須にしない。

- 親識別子、レビューID、対象タスクID、成果物の参照先と版。
- 状態：`reviewed`（依頼された確認を実施）、`input_insufficient`（計画・資料・参照先などの入力不足）、`inconclusive`（確認手段や判断材料の制約により結論が出ない）。`reviewed` でも指摘はあり得る。
- 確認した共通原則と特化観点のID、確認範囲・方法・結果と根拠。特化観点0個ならその理由。確認できなかった範囲は別記する。
- 指摘ごとの識別子、該当タスクID・箇所、関係する原則／特化観点と要求、問題の内容と利用への影響、確認根拠、必要な修正または検証。**必須修正**（合意した要求・制約の違反、利用を阻む問題、具体的なセキュリティ問題）と**改善提案**（完了を妨げない任意の改善）を区別する。
- 未確認事項・不足情報とその影響、エスカレーションを必要とする問い・証拠・既知の試行・阻害要因。指摘なし・相談不要の場合もその旨を記す。

## 指摘への対応と再レビュー

親は指摘の根拠を確認し、採用・不採用・保留と理由を記録する。必須修正を理由なく改善提案へ変更しない。誤検知は具体的な根拠とともに不採用とし、任意の改善は今回の目的に必要なものだけ採用する。条件変更が必要なら既存の計画変更ルールに従う。

採用した修正は元のタスクIDと指摘IDで `artifact-worker` に戻す。作業者が修正・セルフレビューを終えたら、親が同じレビュワーへ変更後の実物を渡し、指摘の解消と変更の影響部分を再レビューさせる。親のタスク検証・全体検証で後から修正した場合も同様とし、古い版へのレビュー結果で完了にしない。変更の影響を受けない確認は再利用できる。

有効な次の修正案や新しい根拠がなく同じ問題が残る場合、理由なく再レビューを繰り返さない。親が未解決の条件を整理し、[任意の相談](escalation.md)や必要なユーザー判断を扱う。レビュワーは親へ相談依頼を返して実行を終え、直接相談せず、相談結果を待つために枠を占有しない。独立レビューと再レビューは通常の品質工程であり、任意相談の最大3回には数えない。相談役の起動は親の共通記録に数える。

役割未登録・枠不足・起動失敗・結果未取得・必須範囲の未確認は独立レビューの成功にしない。親が不足を補い、未完了の実行の回収・停止を管理する。親や作業者の確認、任意の相談結果を独立レビューの代用とせず、確認できた範囲と残る対応を示す。

対象の最新版について独立レビューを終え、すべての指摘に採否と根拠があり、採用した必須修正と完了判断に必要な未確認事項を解消してから、親が[完了条件の検証](verification.md)へ進む。レビューID・対象の版・選んだ観点・指摘の採否・再レビュー結果は親の会話または既存の作業記録に残す。タスク計画MCPに未定義のフィールドを追加したり、Plugin のインストール先に実行記録を書いたりしない。
