# 成果物作成ワークフロー

ユーザーが `artifact-workflow` またはこの Plugin の利用を明示的に指定した場合にのみ適用する。通常の成果物作成依頼だけでは適用しない。

成果物の形式に依存せず、合意した計画に沿って作成を進める。このファイルをワークフローの正本とし、各工程に入るときに対応する参照資料を読む。

親は現在のチャットを担当するエージェントのままとし、タスク分解・計画の提示・承認・委任・成果物の確認・タスクと全体の検証・Delivery を管理する。サブエージェントを利用するのは成果物の生成・修正とそれに伴うセルフレビューのみとし、登録済みの Custom Agent `artifact-worker` を最低1人、同時に最大3人使用する。親が担当する工程にはサブエージェントを追加しない。委任時は役割と作業内容を指定し、Custom Agent の内部設定を参照・選択・上書きしない。

## タスク分解のガードレール

- **Task は作業者が成果物そのものを作成・変更する作業単位**とする。セルフレビュー、動作検証、完了条件の確認、全体検証は、作業タスクに対して行う Workflow の処理である。独立したタスクIDを付けず、修正と再確認も元のタスクIDで追跡する。
- **Delivery は作業タスク群の外に置く**。この Workflow は完成した成果物の提示と、依頼された後続処理への引き渡しまでを管理する。公開・提出・PR 作成などを作業タスクや作業タスクの完了条件へ混ぜない。外部 Skill による後続操作は、その Skill が実行方法を担い、内部手順をこの Workflow の作業タスクへ分解しない。

例えば「この Plugin でウェブサイトを作成し、その後 GitHub 操作 Skill で PR を作成」なら、ウェブサイトを完成させる作業だけをタスク化する。品質確認はそのタスクに対する処理とし、完成後の GitHub 操作 Skill への引き渡しを Delivery に記録する。依頼された後続操作を省略してよいという意味ではない。

## 進め方

1. **タスク分解**：[タスク分解の方針](references/task-planning.md)を読み、成果物を作るための作業だけに一意なタスクIDと、目的・成果物・確認可能な完了条件を定義する。全体の完了条件と Delivery の方法・担当は作業タスクの外に整理する。
2. **計画の提示**：[タスク計画テンプレート](assets/task-plan-template.md)を埋め、二つのガードレールを満たすことを確認してユーザーへ提示する。
3. **人間による承認**：計画を提示した段階で止まり、ユーザーの承認を待つ。修正依頼があれば計画を更新して再提示する。承認を得るまで成果物の生成へ進まない。
4. **成果物の生成**：親が[生成の方針](references/generation.md)を読み、承認済みのタスク計画と依存関係から `artifact-worker` の人数と割り当てを判断する。各担当へ計画と担当タスクIDを渡して生成を委任し、計画と同じタスクIDで成果物を対応付けさせる。
5. **セルフレビュー**：親が[セルフレビューの方針](references/self-review.md)を各担当の `artifact-worker` へ渡し、それぞれが生成した成果物そのものの確認と必要な修正を委任する。生成とまとめて委任してよいが、各担当が生成後にセルフレビューを行い、成果物とレビュー結果を親がタスクIDごとに受け取る。
6. **タスクの完了条件の検証**：親が[検証の方針](references/verification.md)を読み、返された成果物の実物を確認して、タスクIDごとに承認された完了条件と比較する。未充足の条件があれば、同じタスクIDで `artifact-worker` へ修正と必要なセルフレビューを依頼し、親が実物を再検証する。条件を満たしたタスクを完了とする。4〜6は各作業タスクを消化する処理であり、工程ごとの作業タスクを追加しない。
7. **全体検証**：全作業タスクの完了後、親が同じ[検証の方針](references/verification.md)に従い、最終的な成果物を全体の完了条件と照合する。問題は該当する元のタスクIDへ戻して修正・再検証し、全体の条件も満たした時点で成果物完成とする。
8. **Delivery**：親が[引き渡しの方針](references/delivery.md)を読み、完成した成果物と検証結果を利用者へ届ける。依頼された公開・提出・PR 作成などがあれば、完成した成果物を対応する Skill や後続処理へ渡し、その結果または未完了の対応を提示する。

## 承認と完了のルール

- 原則は計画提示後の明示的な承認とする。すでに同じ計画への承認を得ている場合は、再度の承認を求めない。
- ユーザーが今回の作業について承認手続きの省略を明示した場合に限り、その指示と適用範囲を計画に記録して進める。通常の作成依頼や無応答を、計画への承認や省略の指示とみなさない。
- 作業範囲・目的・成果物・完了条件の変更が必要になったら、変更後の計画を提示して承認を得る。承認済みの範囲内での修正に、追加の承認は不要。
- 計画の提示・変更と人間承認の管理は親が行う。`artifact-worker` から計画変更の必要性が報告された場合も、この承認ルールを適用してから該当作業を再委任する。
- `artifact-worker` が利用できない場合は生成を開始せず、親が役割の登録・利用に必要な対応をユーザーへ伝える。
- セルフレビューと完了条件の検証は別工程とする。未充足または確認不能の条件が残る場合は完了扱いにせず、該当タスクIDと不足している情報・必要な対応をユーザーへ伝える。
- 作業タスクの完了、全体検証を経た成果物完成、Delivery の完了を区別する。引き渡し待ちだけを理由に作業タスクを未完了に戻したり、公開・PR 作成のタスクを追加したりしない。依頼された後続操作が残っている場合は、依頼全体が完了したとは報告しない。
