# タスク分解

依頼のうち今回の生成範囲で完成させる成果物を、検証可能な作業タスクに分ける。提出・公開など後続処理の実行は対象外とし、必要な入力と依頼内容を Delivery 欄へ残す。

## 範囲

- 今回の計画には、後続処理の結果を待たずに完成・検証できる成果物だけを含める。
- 後続結果が必要な成果物は、入力取得後に別の生成として計画する。未確定値で完成扱いにしない。
- 依頼が完成済み成果物の提出など後続処理だけなら、計画・workerを用意せず親が選択した手段で進める。
- 後続処理側の作成・編集・実行・検証を、worker の範囲へ含めない。

## タスク境界

- タスクIDを付けるのは成果物そのものを作成・変更する作業。品質確認、独立レビュー、完了検証、提示・引き渡し、後続処理には付けない。
- 必要な成果に合わせて分割し、細分化しすぎない。実行順に影響する依存だけ記載する。
- レビュー・検証記録だけを成果物として扱わない。依頼されたテストコードや検証報告書の作成は作業タスクにできる。
- タスクIDは一意で表示順と独立させ、削除済みIDを再利用しない。
- 責務・依存に沿って分解し、方針を当てるためだけの不自然なタスクを作らない。各タスクに最も具体的に合う共通方針を0〜1件選ぶ。
- 計画案を提示する前に `list_extensions` で登録方針を調べ、各適用候補は `get_extension` で全文と `revision` を取得する。MCP 接続・一覧・取得の失敗は該当なしにせず、どの段階が失敗したか記録する。
- タスクごとに適用方針のID・名前・選定理由、または該当なし/取得失敗の理由を計画案に示す。計画へ適用する候補は全文・依存先・対象とともに固定し、承認対象に含める。生成と独立レビューには同じ固定内容・`revision`・選定理由を渡し、レジストリから選び直さない。
- 今回のユーザーによる明示要求と方針の一部が矛盾する場合は、矛盾する要求・方針の箇所と理由を計画に記録し、その箇所だけを適用しない。他の両立する指示は適用する。矛盾がないのに、計画への記載漏れや計画への承認だけを方針の無効化・今回限りの変更と解釈しない。今回限りの変更は、ユーザーが明示的にその方針の変更・不適用を指示した場合に限る。
- 承認後に方針の選定漏れまたは計画との不一致が判明した場合、生成・委任前に方針と revision を含む修正計画を再提示し、その計画への明示的な承認を得てから保存・作業する。承認前の保存・委任・生成を禁じる既存の手順に従う。
- 更新候補は承認を得るまで保存せず、更新しなくても今回の計画を進める。
- 共通原則と今回のユーザー依頼も適用する。MCP と Skill の記述はモデルの方針遵守を機械的に強制する保証ではない。

## 必須項目

| 項目 | 記載内容 |
| --- | --- |
| タスクID・名前 | 一意なIDと短い作業名 |
| 目的 | 成果物に必要な理由 |
| 成果物 | 確認可能な実物と出力先 |
| 完了条件 | 実物で判定できる内容、制約、期待状態 |
| 依存 | 実行順に影響する先行タスクだけ |

「適切に作る」「品質を高める」だけを完了条件にしない。全体の完了条件には、成果物を組み合わせて今回の生成目的を満たす状態を記す。

## 提示

- [task-plan-template.md](../assets/task-plan-template.md)を使い、記入案内を削除して、範囲・目的・成果物・完了条件をユーザーが判断できる形で提示する。
- 計画に独立した品質タスクや後続処理の実行・成功条件がないことを確認する。
- Delivery 欄には成果物の参照方法、親への引き渡し情報、依頼された後続処理と結果後の依頼だけを書く。実行手順は定義しない。
- 変更後の承認とMCP保存は [承認方針](../../artifact-workflow/references/approval.md)、[計画ライフサイクル](../../artifact-workflow/references/task-memory.md)に従う。承認済み計画の整理も親が行う。
