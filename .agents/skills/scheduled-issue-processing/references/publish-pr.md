# GitHub 反映と PR 作成

[起動条件](startup.md)の優先順で、操作ごとに利用可能な手段を選ぶ。Git 経路のコマンドは [Git 操作](git-operations.md)に従う。どの経路でも、リモートへの反映前とローカル同期の前に作業状態の確認を行い、進行中の操作をコミットで完了させない。ローカルコミットはステージ前とコミット直前にも確認する。

1. 検証・レビュー済みの差分から、GitHub Plugin が提供するコミット・Git object 等の適切な機能でコミットを作成する。Plugin / API 経路ではリモートに必要な object を作成してから ref を作る。Git 経路ではステージ、ステージ全体の差分の照合、コミットと tree・clean の確認を行い、レビュー済みの変更だけをコミットする。不一致やレビュー対象外の変更がある場合は[変更の保全](resume.md#変更の保全)に従って停止し、Push しない。操作と承認方針は [AGENTS.md](../../../../AGENTS.md#git-と-github-の操作)に従う。
2. 新規公開では、リモート ref が存在しない場合だけ作成する操作で Issue 用ブランチへ反映する。Plugin / API 経路では ref 作成を使い、既存 ref があれば失敗することを確認する。Git 経路では、対象と影響（Issue 用 ref の新規作成と、既存 ref があれば更新せず停止すること）についてユーザーの明示的な承認を得た場合だけ、Git 操作の新規 Push を使う。末尾の `:` に続く空の期待値で ref の不存在を検査する。さらに `--porcelain` の出力で対象 ref の行が `*` の新規作成であることを確認し、`=` の up to date を含め、それ以外は再利用・上書きせず停止する。競合した場合は再利用・上書きせず停止する。
   [再開判定](resume.md)で正当に特定された再開作業の既存ブランチへの反映では、対象 ref とその先端 SHA を再取得し、先端が作成したコミットの祖先であることを確認する。Plugin / API 経路では、確認した SHA を期待値とする条件付き fast-forward 更新を使う。GitHub GraphQL の [`updateRefs`](https://docs.github.com/en/graphql/reference/git#updaterefs) では、対象 ref だけを指定し、`beforeOid` に確認した空でない SHA、`afterOid` にレビュー済みコミット SHA、`force` に `false` を渡す。Git 経路では、対象と影響（確認した既存 ref の fast-forward 更新と、削除・先端変更があれば更新せず停止すること）についてユーザーの明示的な承認を得た場合だけ、Git 操作の再開の祖先確認と再開 Push を使う。条件付き更新が利用できない場合は停止する。`--force-with-lease` の承認として、スケジューラの起動や `AI処理可能` ラベルを扱わない。新規・再開とも承認がない場合は Plugin / API 経路を選び、利用できなければ停止して必要な承認を報告する。反映結果が不明な場合はリモートを再取得してから判断する。
3. 選択した手段でリモートブランチを再取得し、リモートブランチの先端 SHA が作成したコミット SHA と一致し、その差分がレビュー済みの差分と一致することを確認する。GitHub 上のレビュー済み変更を確認できない場合は PR を作成しない。
4. ローカル HEAD の tree を反映済みリモートコミットの tree と比較する。一致していなければ Git 操作のステージとステージ全体の差分の照合を行い、コミット前に index の tree がリモートコミットの tree と一致することを確認して、対応するローカルコミットを作成する。作成後または既に一致している場合は、ローカル HEAD の tree がリモートコミットの tree と一致することと、Git 操作の clean の確認で staged、unstaged、untracked file がなく clean であることを確認する。不一致や失敗、レビュー対象外の変更がある場合は[変更の保全](resume.md#変更の保全)に従って停止し、PR を作成しない。
5. 確認後、選択した手段で Issue を参照する Open PR を作成する。PR の base は開始時に確認した default branch、head は Issue 用ブランチとする。

PR 本文に `Closes`、`Fixes`、`Resolves` 等の Issue closing keyword を含めない。PR の merge と Issue の Close は別のライフサイクルとして扱い、Issue はこの Skill では閉じず、人間が必要な確認を終えた後に閉じる。
