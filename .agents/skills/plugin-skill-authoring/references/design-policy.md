# Plugin Skill 設計の方針

## 基本原則

- 一文一責務を基本とし、長い説明文ではなく見出し・箇条書き・ファイル構造で説明する。
- 各情報の正本を一箇所に保つ。入口に詳細を重複記載せず、必要な段階でリンク先を読む。
- 既存の Plugin / Agent Skills / Codex の仕様と、対象リポジトリの動作契約を優先する。
- 対象は配布用 `plugins/*/skills/` と開発用 `.agents/skills/`。配置と配布境界を混同しない。

## AGENTS.md

- 初めに知る必要のある情報だけを記載する。
- 作業に合う Skill を探すための入口と、Git 操作など初期から必要な制約へのリンクを優先する。
- Skill の詳細手順や、初期状態で不要な条件分岐を記載しない。

## SKILL.md

- YAML frontmatter の `name` と `description` を規格に従って記載する。説明には用途と使用条件を含める。
- 本文はタイトル、概要、制約と責務範囲、フローで構成する。
- フローは必要な場合に番号付きで順序を示す。処理・分岐の詳細は参照先で説明する。
- 制約は短い独立した項目で列挙する。該当する制約を持たない Skill に架空の制約を作らない。
- 読んだ時点で Skill の役割と全体の流れが分かる粒度を保つ。

## リンクと日本語の表現

- Skill を利用する場合は `[Skill 名](SKILL.md への相対パス)を使う。` を基本形とする。
- 文書に規定された方針を利用する場合は `[〇〇の方針](相対パスまたは URL)に従う。` を基本形とする。
- 後続の具体的処理が必要なら「を使って、〇〇する」「に従って、〇〇する」と続ける。フローの動詞を二種類に限定しない。
- リンクの表示名で依存先の意味が分かるようにし、参照先のファイルパスを明記する。
- 単なる情報資料や API 仕様の取得を、無理に「方針に従う」とは表現しない。

## 情報の配置

| 場所 | 責務 |
| --- | --- |
| `references/` | その Skill だけが使用する詳細手順、観点、資料 |
| `docs/` | 複数の Skill や AGENTS.md から参照される横断方針・仕様 |
| `assets/` | ユーザーへの問い合わせ、Agent 間受け渡し、出力形式などの定型テンプレート |
| `scripts/` | 手順や検証のうち、決定論的に処理できる部分 |

- テンプレートの配置と呼び出しは対象 Plugin / Skill の仕様に従う。
- 参照先が配布物に含まれる必要がある場合、Plugin のパッケージ内で参照を解決できるようにする。
- 共通方針を複数の Skill 配下へコピーしない。共有の正本を `docs/` に置く。

## 動詞の定義

| 動詞 | 意味 |
| --- | --- |
| 参照する | 情報を取得し、判断材料にする |
| 適用する | 指定された規則・観点を処理に反映する |
| 呼び出す | 別の Skill を起動する |
| 委譲する | 別の Agent に作業を任せる |
| 実行する | 手順や処理を実施する |
| 検証する | 明確な完了条件への適合を判定する |
| レビューする | 品質・妥当性を評価する |
| 提示する | 結果や判断材料をユーザーに示す |

Skill にリンクする指示表現では「呼び出す」より「使う」を優先する。動詞の使い分けは意味を明確にするためであり、作業の実施方法を不自然に制限しない。

## 検証

1. `node .agents/skills/plugin-skill-authoring/scripts/validate-skill.ts <対象の SKILL.md>` を実行する。複数の対象を渡せる。
2. `npm run test:infrastructure` など、対象に関係する既存の自動テストを実行する。
3. 配布 Skill なら、既存の Plugin 構成テストとパッケージ内リンク検証も実行する。
4. スクリプトで確認できない責務分離、文意、リンク名、フローの自然さは人が読める判断材料としてレビューする。

構造検証スクリプトは全ての文章の意味や Plugin 仕様への適合を保証しない。既存のスクリプト・テストを優先して再利用し、同じ検証をプロンプトに重複実装しない。
